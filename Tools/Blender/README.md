# SimuLean 3D asset pipeline (Blender, script-built)

Every asset in `Assets/SimuLean.Unity/Art/Models/` is **generated by a Python
script** run headless in Blender. Nothing is hand-modelled, so an asset can be
rebuilt, re-coloured or re-budgeted by editing numbers and re-running.

```
Tools/Blender/
  simulean_kit.py         geometry kit: Part builder (bmesh), sweeps/lathes, bevel+normals
                          finishing, atlas unwrap, PBR bake, LOD generation, FBX export
  simulean_materials.py   procedural Cycles materials (paint with wear/grime/decals,
                          steel, rubber, lenses...) that get baked into the atlas
  simulean_modular.py     modular-kit pipeline: many FBX pieces, one shared atlas
                          (Piece, seamless-tiling bake, per-piece LODs and export)
  assets/<name>.py        one script per asset (forklift.py, rail_shuttle.py, gantry_stacker.py, ship_block.py,
                          block_workspace.py, level_luffing_crane.py, spmt.py, goliath_crane.py
                          --variant goliath|welding) or kit (ship_items.py, shipyard_people.py)
                          (industrial_building.py, overhead_crane.py)
  assets/workshop_preview.py  assembles both kits into a 24 x 18 m workshop and renders it
  export_flexsim.py       re-export a built asset for FlexSim
  previews/               turntable/LOD renders written by each asset script (git-ignored)
  build/                  regenerable .blend sources (git-ignored)
```

## Running

Blender 5.x, no add-ons (`--factory-startup`). A GPU is used for the bake when one
**actually bakes**: `setup_cycles_gpu` tries OptiX, CUDA, HIP, oneAPI, Metal in turn and
keeps the first whose 16 px probe bake (`_device_bakes`) comes out non-black, else the CPU.
On the development machine (RTX 4050) OptiX's kernels do not compile and bake all-black
*without an error*, so CUDA is chosen. `bake_texture_set` also refuses to write a set whose
albedo or AO came out all black. (Before 2026-10-07 the first listed backend was trusted:
that shipped a black Forklift atlas in commit `fbd5990`.)

```bash
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" -b --factory-startup -P Tools/Blender/assets/forklift.py -- --quick
```

| flag | meaning |
|---|---|
| `--quick` | 1024 px bake and small preview renders (~1 min). Use while iterating. |
| `--bake 4096 --save 2048` | Production run: bake at 4096 and downsample to 2048. The supersampling cleans up edge wear. |
| `--paint yellow\|orange\|red\|blue` | Colour variant. Only `yellow` writes the FBX. Other colours write an extra texture set `<Name>_<Colour>_*.png`, which uses the same UVs and so the same mesh. |
| `--no-render` | Skip the preview renders. |
| `--cpu` | Bake and render on the CPU (forklift, rail shuttle, gantry stacker, AGV, operator). |

### Exporting for FlexSim (comparison / reuse)

```bash
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" -b --factory-startup -P Tools/Blender/export_flexsim.py -- --asset Forklift
```

This reads `build/<Asset>.blend` and writes files to `build/FlexSim/`:

- `<Asset>_LOD0/1/2.fbx`, with embedded textures;
- a `.glb` fallback for each LOD.

The files are prepared for FlexSim as follows:

- Z-up, in metres.
- Facing +X, which is FlexSim's travel direction.
- Asset hierarchy only, with no preview props.
- Baked AO multiplied into the albedo, because FlexSim has no occlusion input.

## Modular kits (building, overhead crane)

`industrial_building.py` and `overhead_crane.py` don't write one model. They
write a **kit**: one FBX per piece in `Art/Models/<Kit>/` (`Wall_Panel.fbx`,
`EndTruck.fbx`, ...), all sharing one texture set `<Kit>_*.png`. Same flags
as above. The Unity components in `Assets/SimuLean.Unity/Visuals/Building/`
lay the pieces out, stretch the tiling ones and merge them
(architecture §4.7.1).

```bash
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" -b --factory-startup -P Tools/Blender/assets/overhead_crane.py -- --quick
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" -b --factory-startup -P Tools/Blender/assets/workshop_preview.py -- --quick
```

`workshop_preview.py` needs both kits built first. It appends them from
`build/*.blend`, not from the FBXs, and writes `previews/workshop_*.png`
and `build/Workshop.blend`.

Kit rules (see the `simulean_modular.py` docstring):

- **Authored frame = Unity frame.** Authored +X is Unity +X, authored +Y is
  Unity +Z, and authored +Z is Unity up. `rotate_to_export` turns the kit
  180° about Z just before export, so the standard FBX mapping lands on that
  frame. An authored Rz(θ) is Unity `Euler(0, −θ, 0)`.
- **Piece kinds:**
  - A `segment` spans exactly `[0, period]` along its tiling axis and is open
    at both ends.
  - A `cap` has its joint at 0 and extends to the negative side. The far end
    reuses it rotated 180°.
  - A `fixed` piece keeps its aspect ratio and may carry named nodes.
- **Strip rule** (shared by `simulean_modular.strip` and Unity's
  `ModularKit.Strip`):
  - `n = round(run / period)` segments, each stretched by `run / (n·period)`;
  - caps outside the run;
  - an optional centre piece, e.g. the girder logo panel.
- **Seamless tiling:**
  - noise is periodic along the tiling axes;
  - the bake surrounds each tiling piece with ghost neighbours, so AO and
    grime cross the joints;
  - tiling pieces are never decimated, only stripped of small parts at far
    LODs.
- **Building grid** is 2 m × 1 m: a 1 m plinth, 1 m panel rows and a 0.18 m
  coping. The doors occupy whole cells: a sectional door is 2 × 4 and a
  personnel door is 1 × 3.

## Operator (MPFB / MakeHuman)

`assets/operator.py` generates the operator with **MPFB 2** (MakeHuman for Blender): a MakeHuman body
(low-poly proxy `male1591` / `female1605`, skin, eyes, eyebrows, hair `short02` / `ponytail01`), the

(`makehuman_system_assets` pack) are CC0, so the generated FBX / textures are too.

**Requirements:** Blender 5.x with the MPFB extension (2.0.17+, *Get Extensions*) and the
`makehuman_system_assets_cc0.zip` pack loaded (*MPFB ▸ Apply assets ▸ Library Settings ▸ Load pack from
zip file*). Run **without** `--factory-startup` (it would disable the extension):

```bash
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" -b -P Tools/Blender/assets/operator.py -- --bake 4096 --save 2048
```

| FBX | what | LOD0 / LOD1 / LOD2 tris |
|---|---|---|
| `Operator` | male look: one skinned mesh `Operator_LOD0..2` + `Helmet_LOD0/1` | 10.6 k / 3.7 k / 1.3 k (+ hat 0.35 k) |
| `Operator_Female` | female look (a kit piece: the folder material `Operator.mat`) | 11.7 k / 4.1 k / 1.4 k (+ hat) |

Both share one atlas `Operator_*` (MakeHuman's own UV islands packed, not re-projected, so the faces
keep their resolution; our vest / hat are projected). The albedo is **RGBA** (hair / eyebrow cards

rest rotations, so `UnityVehicleAnimator` turns them **relative to rest** about the model's lateral
axis. `Operator.prefab` holds both looks and `OperatorAppearance` (gender Male / Female / Mixed,
helmet). `build_preview(look, helmet)` builds the dressed rig in an open Blender without baking.

## Level-luffing crane (shipyard)

`assets/level_luffing_crane.py` builds a double-link level-luffing portal crane ("grúa cigüeña").
It writes one FBX, `Art/Models/LevelLuffingCrane/LevelLuffingCrane.fbx`, with
`LevelLuffingCrane_*.png` and `LevelLuffingCrane.mat`. LOD0 / LOD1 / LOD2 have 9.8 k / 6.8 k /
2.8 k tris on 7 renderers.

The crane has:
- a white portal on four 4-wheel bogies, gauge 10.5 m, rails along local Z, with a ladder, a top
  walkway and a power-cable reel;
- a slewing deck with the machinery house, counterweight, A-frame and a blue cab;
- a 24 m box boom with a walkway;
- a 19.2 m jib (5 m tail) marked `SWL 40 t`, with the hoist ropes running along it;
- a tie from the A-frame top to the jib tail;
- two rope falls and a hook block.

**Linkage.** The four bars were found by a numerical search for the flattest tip path. The
coordinates are in the slewing plane, in metres, with x towards the jib and y up from the rail
top.
- Boom foot F = (2.0, 16.0), A-frame top A = (−6.0, 19.1).
- Boom 24.0, jib tail 5.0, tie 24.7, jib nose 14.2.
- Boom angle 38–80° gives a reach of 35.1–16.8 m. The tip stays at 31.2–32.1 m, so the hook
  barely moves when the crane luffs.
- The export is at rest pose: boom at 56°, reach 29 m.
- `linkage(theta)` in the script returns B, R and T for any boom angle.

**Nodes in Unity.** The crane faces +X at rest and its pivot is the rail-top centre.

| node | parent | what to drive |
|---|---|---|
| root | — | travel along local Z (the rails) |
| `Slew` | root | rotation about local Y (pivot 13.4 m up) |
| `Boom` | `Slew` | local Z rotation = θ − 56° (raising is positive) |
| `Jib` | `Boom` | local Z rotation = (α − α₀) − (θ − 56°). α is the jib angle from `linkage`; α₀ is its value at rest |
| `Tie` | `Slew` | local Z rotation = β − β₀. β is the angle of the line A→R |
| `Ropes` | `Slew` | `localScale.y` = drop. The unit strands hang 1 m below the tip sheave; put the node at the tip: (Tx, Tz − 0.5 − 13.4, 0) |
| `HookBlock` | `Slew` | the `Ropes` position − (0, drop, 0) |

The sockets are `JibTip` (under `Jib`), `TieEnd` (under `Tie`, the jib-tail pin) and
`HookSocket` (under `HookBlock`, where the load attaches).

In Unity, the member prefab `Prefabs/ResourceMembers/LevelLuffingCrane` carries `LevelLuffingCraneView`, which applies
this table: in a resource team with Axes travel, the hook follows the member's axes. In Blender, `build_scene()` builds a preview rig. `pose(theta, slew, drop)` poses it exactly as
the table above describes.

## In Unity

The models are used by the SimuLean Library's presets (`Assets/SimuLean.Unity/Editor/LibraryPresets.cs`): a station
is an element + `StationModel` (the chosen model as the child `Model`, its work socket bound to the item position) +
`MachineStateView` (the `Beacon` lamps and the moving nodes named in each script's docstring); people, porters and
vehicles are member prefabs (`Prefabs/ResourceMembers`); pallets, totes, roll cages and patients are item prefabs
(`Prefabs/Items`). Keep node names stable: the views find them by name.

## Methodology

1. **Parts.** Each asset is built as named parts (`Part` → bmesh). Each part is
   finished with angle-limited bevels (40° by default), then triangulation, then
   auto-smooth, then a WeightedNormal pass. This gives crisp hard-surface
   highlights without subdivision.
2. **One atlas.** All parts share a single UV atlas. Texel density is set per
   part (`TEXEL_WEIGHTS`): big painted panels get more, hidden axles get less.
   Parts stay **separate objects through the bake**. The edge-wear mask is
   inside-AO with `only_local`, so parts that touch or interpenetrate never chip
   each other.
3. **Bake.** The procedural materials are baked to one Unity Standard PBR set:
   `_Albedo`, `_MetallicSmoothness` (R = metal, A = smoothness), `_Normal`
   (OpenGL, MikkTSpace), `_Occlusion` and `_Emission`. The bake margin uses
   `ADJACENT_FACES`, which continues texels across UV seams so dark
   neighbouring islands can't bleed into them.
4. **LODs.** Levels come from COLLAPSE decimation with UVs preserved, so every
   LOD reuses the same material and atlas. Normals are re-sharpened and
   re-weighted afterwards. Far LODs also merge renderers to cut draw calls
   (see *Performance*).
5. **Rig.** Every animated part is an **Empty** (a bare Unity Transform) with
   its meshes hanging under it as `<Name>_LOD0/1/2` at identity.
   `export_fbx` converts the axes itself, so Blender -Y (front) becomes Unity +Z
   and every node has an identity rotation. Before export it sets each node's
   local matrix to `G·L·G⁻¹` and each mesh to `G·v`; the exporter's
   `bake_space_transform` stays **off**.

## Conventions (the Unity side relies on these)

- Output goes to `Assets/SimuLean.Unity/Art/Models/<Name>/<Name>.fbx`, with the
  maps named `<Name>_<Map>.png` next to it.

  > ⚠️ **Don't** name the folder `Library`. The root `.gitignore` rule
  > `[Ll]ibrary/` is unanchored and would silently ignore it.

- Mesh objects end in `_LOD<n>`. **Animate the named parent transform, never
  a `_LODn` mesh**, because the mesh behind a name changes with distance and
  some parts are merged into `Body` at far LODs.
- The pivots and axes of each animated node are documented in the asset
  script's docstring (e.g. the forklift's `Mast` tilts about local X, while
  `MastInner` and `Carriage` lift along local Y).
- There is one material per asset.

`Assets/SimuLean.Unity/Editor/Tools/SimuLeanModelPostprocessor.cs` applies these
conventions on import, for any model under `Art/Models/`:

- It sets up the textures: `_Normal` is imported as a normal map, and the masks
  are imported as linear.
- It creates `<Name>.mat`: Standard shader, all maps wired, **GPU instancing on**.
  Each extra colour set gets its own material, e.g. `<Name>_Orange.mat`.
- It assigns that one material to every renderer.
- It replaces Unity's per-node auto-LODGroups with **one LODGroup on the model
  root**:

  | Level | Shown while the model is at least… of screen height |
  |---|---|
  | LOD0 | 25% |
  | LOD1 | 7% |
  | LOD2 | 1% (culled below) |

- LOD2 renderers don't cast shadows.
- A **kit piece** is an FBX not named after its folder, e.g. `Wall_Panel.fbx`
  in `IndustrialBuilding/`. For kit pieces the postprocessor also:
  - uses the folder material `<Folder>.mat`;
  - imports the meshes *readable*, so Unity can merge them into chunks.

`Tools ▸ SimuLean ▸ Reimport 3D Model Library` re-applies all of this.

## Performance budget

The target is scenes with **dozens of animated vehicles**. The measured forklift:

| LOD | triangles | renderers | used when |
|---|---:|---:|---|
| LOD0 | ~22 k | 11 | close-up (> 25 % screen height) |
| LOD1 | ~6 k | 10 | mid-range (7–25 %) |
| LOD2 | ~1.8 k | 4 | far (1–7 %); only lift and tilt remain visible |

In a typical overview camera most vehicles sit at LOD1 or LOD2. Forty forklifts
then add up to roughly 100–250 k triangles, which is negligible for any
discrete GPU.

Draw calls matter more than triangles. They are kept low by:

- one shared material with instancing;
- merging parts into `Body` at far LODs;
- disabling shadow casting at LOD2.

Budgets for new assets:

| | LOD0 | LOD1 | LOD2 |
|---|---:|---:|---:|
| Mobile equipment (forklift, AGV, tugger) | ≤ 25 k tris, ≤ 12 renderers | ≈ 25–30 % of LOD0 | ≤ 2 k tris, ≤ 4 renderers |
| Static equipment | ≤ 1 renderer per moving part | | |

**Lessons from the kits:**

- **Texel weights.** One atlas serves the whole kit, so large flat painted
  areas (wall sheets, girder webs, door leaves) get *low* weights, around
  0.3–0.6. Small or thin hardware gets *high* ones, up to 2.6 for the crane
  rail, whose flanks are only 20 mm tall. Otherwise the big surfaces eat the
  atlas and the rail blurs to a couple of texels.
- **Bake margin.** Kit islands sit only a small gap apart, and Blender writes
  each object's bleed in turn. So `bake_kit` keeps the margin below half the
  island gap, instead of the default 16 px that paints over the neighbours.
- **Text decals.** `render_text_image(bold_offset=...)` thickens the glyphs
  with a round dilation of the rendered image. Never use the font curve's
  `offset`: at sharp glyph corners it leaves long miter spikes, which also
  inflate the measured aspect ratio. About 0.015 gives a bold weight with
  Bahnschrift.
- **Never use the FBX exporter's `bake_space_transform`.** It is only correct
  for the root and its direct children. Deeper nodes (`Beacon_LOD0`, `Bay_A`,
  `LoadSocket`, every `<Node>_LOD0` under a node) came out with swapped y/z
  offsets and a 90° X rotation (found 2026-09-26). `export_fbx` now does the
  conversion itself. FBXs exported before that fix need re-exporting: the
  Forklift is affected.
- **Don't re-import the FBX into Blender for previews.** Preview scenes append
  the `.blend` instead.

## Adding an asset

1. Copy the structure of `assets/forklift.py`:
   - `build_*()` part builders;
   - a `LOD_PLAN` with ratios per part (`None` drops the part at that level);
   - `NODE_PIVOTS` / `NODE_PARENTS` for the rig.
2. Iterate with `--quick` and check `previews/`.
3. Document the animation contract (node names, axes, ranges) in the script
   docstring.
4. Run the production bake, then open Unity. The postprocessor does the rest.
